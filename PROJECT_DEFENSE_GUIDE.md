## 1. The project on one page

**Goal (from the subject).** Exploit cybersecurity text to (a) classify incidents, (b) extract entities, (c) build an incident/entity knowledge graph with clusters and important relations,
(d) apply GNN/GTN, (e) answer security questions with RAG and Graph-RAG (Neo4j in the course), and deliver (1) the graph and (2) a model that classifies, answers and finds threat↔target relations.

**Data (the first thing to say).** `AlicanKiraz0/Cybersecurity-Dataset-v1`: 2,411 (question, answer) pairs, **LLM-generated, about security *concepts* — not real incident reports — and without labels**.
So "incident" means "Q&A record", categories are *weak labels* from keyword rules, and I measured how weak they are (§3.3).

**What I built.** A package `cyberintel/` (data → NER → relations → graph → classification → GNN/GTN → hybrid retrieval → Graph-RAG → backend service) and a 6-view Streamlit app, with 57 automated tests.

## 3. Component by component

### 3.1 Data and the audit of the prototype
* **What was there:** a working flat prototype (7 scripts). I audited it before touching anything (`docs/AUDIT_REPORT.md`) and reproduced its numbers exactly (macro-F1 0.5404, GCN 0.4694 < MLP 0.5241, hit@5 0.825 vs 0.835).
* **Why an audit:** the subject says "do not assume existing code is correct". The audit found 6 real problems: leaked chain-of-thought in 211 rows, answers truncated to 1,500 chars (half the CVE mentions lost), weak labels that were not "mostly from the question", **incomparable splits** between models, a QA demo that answered "Which vulnerability affects log4j?" with an unrelated passage, and circular retrieval evaluation.
* **Decision:** keep the working ideas (weak labels as a baseline, `Embedder`, co-occurrence+lift, pure-torch GCN), rebuild the rest in a package, keep the original code in `legacy_prototype/`.
* **Likely question:** *"Why not just use the dataset's labels?"* → there are none (columns `system`, `user`, `assistant`).

### 3.2 Cleaning (`data.py`) — `reports/data_quality.json`
* **354** answers contain `<think>`, **201** never close it (generation cut inside the reasoning → no final answer). Those rows are dropped; elsewhere **568** first-person reasoning sentences ("I need to…", "the user wants…") were removed from 234 rows at *sentence level* (not whole rows). Literal `\n` in 524 answers → spaces. 15 duplicate questions removed. Result: 2,411 → **2,193** rows.
* **Why sentence-level and not "drop every suspicious row":** it keeps real content from rows that mix reasoning and answer.
* **Why the full answer is kept:** the prototype cut at 1,500 chars; the raw text holds **95 distinct CVEs**, the prototype saw 39. Now NER finds 86 after cleaning.
* **Known cost:** dropping unfinished-reasoning rows loses a few facts (e.g. CVE-2018-1002105/Kubernetes); the reference KB covers that one (QA items A03/B06 are flagged `kb_only`).
* **Splits:** one stratified train/val/test (70/10/20 → 1,534/220/439), stored in the corpus, used by *every* model. **Why:** the prototype's metrics came from three different splits and could not be compared.

### 3.3 Labels: weak vs gold (`labels.py`, `annotations/gold_labels.csv`)
* **Weak labels:** keyword rules (11 classes, `ransomware` merged into `malware` because only 18 rows). Cheap but circular with keyword-based models.
* **Gold labels:** 183 test-split records annotated by topic of the question, **blind to the weak labels**. Rules agree with gold on **67.2 %**; Cohen's κ 0.63.
* **Why both are reported always:** accuracy against rules measures *rule reconstruction*; accuracy against gold measures *topic understanding*.
* **Why the gold sample comes from the test split:** models are trained on weak labels of the train split only; gold rows are then unseen.
* **Limit (say it):** the annotator is an AI assistant, 1 annotator, so no inter-annotator agreement; `phishing` has 1 gold example. The student's review column `human_label` is waiting.
* **Likely question:** *"Why trust Claude's labels?"* → I don't claim they are ground truth; they are an independent second opinion that differs from the rules on 33 % of records and is the best available; the review procedure is documented.

### 3.4 Preprocessing and vectorisation (AA3) — `preprocessing.py`, `embeddings.py`
* Implemented the course steps: normalisation, tokenisation, stop words, **Porter stemming**, **WordNet lemmatisation**, **POS tags** (visible in the UI "Incident analysis").
* **Measured effect on classification** (LogReg, test macro-F1, weak labels): raw 0.631 · +stop words 0.631 · +stemming 0.626 · +lemmatisation 0.630 → **differences ≤ 0.005: preprocessing choices do not matter here** (TF-IDF with sub-linear tf already down-weights function words).
* **Vectorisation:** TF-IDF (1–2 grams, sub-linear tf) and its LSA projection (SVD, 128-d); contextual **MiniLM** embeddings. **Cosine similarity** everywhere (kNN graph, retrieval).
* **LDA** (course NLU task): 10 unsupervised topics, NMI with the weak labels 0.239 → the keyword taxonomy and unsupervised topics only partly agree (`reports/topics.json`).
* **Why not Word2Vec/GloVe:** static embeddings trained on 2k documents are poor; pretrained contextual embeddings (MiniLM) were available.
* **Fitting rule:** every vectoriser inside an experiment is fitted on the train split only.

### 3.5 Classification (`classify.py`, `transformers_exp.py`) — `reports/classification.json`

| Model | val macro-F1 | test (weak) | **gold macro-F1** | gold acc |
|---|---|---|---|---|
| majority | – | 0.043 | – | 0.126 |
| **TF-IDF + LogReg** | 0.605 | 0.646 | **0.644** | 0.705 |
| TF-IDF + linear SVM | 0.601 | 0.670 | 0.641 | 0.716 |
| TF-IDF + ComplementNB | 0.500 | 0.559 | 0.579 | 0.689 |
| LSA + MLP | 0.529 | 0.589 | 0.622 | 0.678 |

* **Protocol:** hyper-parameters chosen on **val** only, **test** touched once; class-weighted losses; macro-F1 because classes are imbalanced (accuracy would reward the majority class).
* **Reading:** TF-IDF ≥ MiniLM ≥ DistilBERT. With ~1.5k training records, labels that come from keywords and a vocabulary-driven task, simple lexical models win; the gold set (183) means gaps < ~0.05 are noise.
* **Why DistilBERT and MiniLM:** AA5 asks to experiment with Transformers; CPU-only machine → small models (66M / 22M parameters). **Why not a bigger LLM:** no GPU, no API key.
* **Likely question:** *"Why did the Transformer lose?"* → small data, noisy keyword labels, 3 epochs / 160 tokens on CPU; the Transformer shines when meaning, not keywords, defines the label. I report it as is rather than hiding it.

### 3.6 NER (AA3) — `ner.py`, `lexicon.py` — `reports/ner.json`
* **Method:** regex for structured identifiers (CVE, CWE, ATT&CK id, IP, hash) + gazetteers (311 canonical names, each with its alias patterns; 49 ATT&CK technique names) for 10 more types (malware, threat actor, software, tool, technology, attack, named vulnerability, defence, ATT&CK tactic, generic target) with **normalisation** (aliases → one canonical name: "Log4Shell", "log4j" → *Apache Log4j*).
* **Why rule-based:** there is **no annotated NER data**; generic pretrained NER (PER/ORG/LOC) does not know CVEs or malware; rules are transparent, offline and *measurable*.
* **Details that matter:** IP validation (rejects `3.6.5.2 Classification…` section numbers and versions); case-sensitive patterns for ambiguous words (*Windows* vs "time windows", *Java* vs JavaScript, *Exchange* only with "Microsoft/Server"); URLs masked so `https://github.com/…/commit/<sha>` is neither "HTTPS" nor a malware hash; inflections for attacks/defences ("heap spraying").
* **Evaluation (entity-level: type + canonical name):**
  * `dev` passages (36 gold entities): F1 1.00 — **not meaningful**, the lexicon was tuned on them;
  * `test` (32): P 1.00 R 0.84 F1 0.92 — **optimistic**, the lexicon was extended after I had read these passages;
  * **`final` fresh sample (58 entities, annotated after freezing): P 0.971, R 0.586, F1 0.731** ← the number to quote;
  * precision audit over 137 random mentions of all types: **97.1 %** (4 errors: 3 git commit SHAs typed HASH, 1 "process monitoring" typed TOOL; both causes fixed afterwards).
* **Honest reading:** very precise, but only 59 % of the entities are found: product/attack names outside the lexicon (Xen, KVM, Dropbox, "Diamond Ticket"…). The fix would be a supervised NER trained on annotated data (none exists) or growing the lexicon.
* **Other facts:** 38,536 mentions; 86 unique CVEs; 2,050 of 2,193 records have ≥ 1 specific entity; 28 of 86 ATT&CK ids map to a technique name (the others are deprecated/ICS ids or unknown to my table).
* **Likely question:** *"Your recall is 59 %, why present it?"* → because measured recall on an unbiased sample is the honest figure; the dev/test numbers are inflated by my own tuning and I say so.

### 3.7 Relation extraction and the knowledge graph (`kg.py`) — `reports/graph_stats.json`
* **Course link:** Chap. 1 "text → graph", Chap. 4 "NER → relation extraction → graph".
* **Method:** two entities form a candidate relation only if they are in the **same sentence** within 120 characters; the relation **label** comes from a typed, directed schema (e.g. DEFENSE→ATTACK = `MITIGATES`, CVE→SOFTWARE = `AFFECTS`, ATTACK→TARGET = `TARGETS`). CVE/vulnerability-name heads link to the **nearest** software only ("CVE-2017-5123 (Firefox) and CVE-2020-6463 (Chrome)" must not cross-link).
* **Strength of a relation:** *support* = number of distinct incidents with the pattern; *lift* = support·N / (df_a·df_b) (association relative to chance). Kept if support ≥ 2 and lift ≥ 1 (≥ 1.3 when the tail is a generic target); single-evidence links are kept for CVEs (rare, precise).
* **Provenance on every edge:** up to 3 evidence sentences with incident ids. This is what makes answers auditable (course: "Graph-RAG traceability").
* **Why this beats the prototype:** it used document-level co-occurrence (two entities anywhere in a 3,000-char answer), undirected, labelled by type pair, and only 3 `AFFECTS` edges existed. Now: sentence-level, directed, evidence-backed; e.g. *ASLR MITIGATES ROP* (29 incidents), *WAF MITIGATES SQL injection*, *SameSite cookies MITIGATES CSRF*, *Golden ticket TARGETS Kerberos*.
* **Reference KB (`resources/kb.json`, 21 CVEs):** a small, hand-curated list of famous CVEs (Log4Shell, EternalBlue, Heartbleed, Dirty COW, Zerologon…) with the affected product. **Why:** the corpus has almost no CVE→software information and is LLM-written; the KB (a) fills the gap with explicit provenance `reference_kb` and (b) lets the system **fact-check the corpus**: of the corpus claims it can judge, **14 verified, 5 differ, 2 contradicted** — e.g. the corpus says EternalBlue is CVE-2017-0290 (the KB: CVE-2017-0144; 0290 is a Windows Defender engine bug) and that Spectre is CVE-2018-3646 (the KB: CVE-2017-5715/5753; 3646 is L1TF/Foreshadow). The 5 "differs" cases are corpus pairs the KB does not list (e.g. PrintNightmare–SMB, CVE-2019-5736–runC instead of Docker). **Limit:** I wrote the KB from public knowledge (NVD/vendor advisories) and it covers only 21 CVEs; re-verify before citing outside the project.
* **Graph size:** 2,193 incident nodes + 517 entity nodes (14 types); 13,660 `MENTIONS`, 11,932 `SIMILAR_TO` (kNN, k=8, cosine ≥ 0.25), 378 semantic relations (327 from the corpus, 51 from the reference KB). Entity graph: 517 nodes, 364 edges, 255 components (largest 248): it is **sparse**.
* **Likely question:** *"Is a co-occurrence relation really a relation?"* → no; it is a *candidate* relation with the type-pair label and evidence. Precision of relation *labels* was **not** measured (no gold relations); I only measured entity NER and the KB agreement. That is a stated limit.

### 3.8 Graph analysis (`graph_analysis.py`)
* **Clusters:** Louvain (modularity maximisation) on the union of the similarity and shared-entity graphs → 12 incident communities; weighted purity vs weak labels **0.48**, NMI **0.25** → clusters are thematic (memory exploitation, web/injection, crypto, Kerberos/AD, firmware…) rather than copies of the keyword taxonomy; each is described by TF-IDF terms and top entities (`reports/incident_communities.csv`).
* **Centrality:** PageRank on the entity graph (Windows, JavaScript, Linux, Intel top): useful for "important entities".
* **Exports:** GraphML (Gephi), Neo4j CSV/Cypher.
* **Likely question:** *"Why Louvain?"* → standard, fast, no k to choose, works on weighted graphs.

### 3.9 GNN / GTN and link prediction (AA7) — `gnn.py`, `linkpred.py` — `reports/gnn.json`, `reports/linkpred.json`
* **Purpose (the subject says "no GNN just for demonstration"):** two evaluable questions. (1) Does *relational context* (similar incidents, shared entities) improve topic classification beyond the text features? (2) Can the graph *discover* missing entity relations (link prediction)?
* **Models, all written from scratch in torch:** MLP (no graph), **GCN** (Kipf & Welling), **GraphSAGE** (mean), **GAT** (additive attention), **GTN** — a Graph Transformer: multi-head scaled dot-product attention restricted to neighbours, **learnable per-edge-type bias** (similarity vs shared-entity edge = heterogeneous graph), residual + LayerNorm + FFN, optional Laplacian positional encoding. Attention is computed on the edge list with a scatter-softmax (same maths as masked dense attention, ~10× faster).
* **Protocol:** same features, same split, class-weighted loss, model selection on val macro-F1, early stopping, **5 seeds, mean ± std**, transductive (val/test labels never used).

* **Reading:** with minilm features the MLP (no graph) scores 0.642; the graph models rank GTN 0.653 > SAGE 0.635 > GCN 0.582 > GAT 0.573. The best graph model is 0.011 macro-F1 above the MLP (0.7 seed standard deviations). Hypothesis (consistent with the homophily numbers below but not tested in isolation): models that mix every feature of a node with its neighbours' (GCN, GAT) lose the discriminative words of the node itself, whereas SAGE and the GTN keep a separate path for the node's own representation. The prototype's 'GCN < MLP' gap persists under the shared protocol: GCN is 0.060 below the MLP (4 seed standard deviations), so it is a real effect and not an artefact of the earlier split. On the 183-record gold subset all models are within about 0.02 of each other, i.e. indistinguishable.
* **Why the graph does not beat the MLP (the investigation the prototype lacked):**
  1. *Homophily.* A GNN smooths a node with its neighbours; that helps only if neighbours share the label. Measured edge homophily (weak labels): similarity graph **0.52**, shared-entity graph **0.38**, combined 0.39, against 0.17 for random pairs — so about half of the similarity edges join incidents with *different* weak labels.
  2. *Redundancy.* The similarity graph is built from the same text embeddings the node features come from — the neighbours add little *new* information.
  3. *Noisy labels.* The labels come from keyword rules on the text; the text features already predict them. Label propagation (graph only, no text features) reaches 0.52 on the similarity graph and 0.32–0.38 on the entity graphs, against 0.64 for the MLP: the graph carries real but weaker signal, and the similarity-graph signal is itself derived from the text.
  4. The prototype's GCN also used a different split and a single seed; under the shared protocol the GCN-vs-MLP gap **persists** (it is real), while SAGE and the GTN, which keep the node's own representation, match the MLP within seed noise.

### 3.10 Retrieval, RAG and Graph-RAG (AA8) — `rag/*` — `reports/qa_eval.json`
* **Knowledge base & chunking:** 11,163 sentence-aligned chunks (≈ 570 chars, question prefixed for context) — course Chap. 4 "chunking".
* **Retriever:** dense MiniLM embeddings **and** lexical TF-IDF over the *full* vocabulary, fused by **Reciprocal Rank Fusion** (Σ 1/(60+rank)). **Why hybrid:** dense models blur rare identifiers ("log4j", CVE ids); lexical search is exact on them; RRF avoids calibrating two score scales. (The prototype's TF-IDF dropped words with `min_df=2`, so "log4j" was not even in its vocabulary.)
* **Three systems compared:** *vector* (dense only) · *hybrid* (dense + lexical) · *graph* (hybrid + graph retrieval).
* **Graph-RAG steps:** (1) **entity linking** of the question (NER + case-insensitive label match); (2) **intent routing** (rules, EN/FR): vulnerabilities-of-software, software-of-CVE, incidents-of-entity, targets-of-attack, mitigations, relation-between-two-entities, similar incidents, describe, general; (3) **graph facts** from the `GraphStore` (relations with support, source, KB verdict, evidence sentences); (4) **graph-aware re-ranking** and entity-driven candidates for "which incidents mention X?"; (5) **evidence-sufficiency gate** → abstain; (6) **generation** (extractive by default); (7) **grounding check**.
* **Abstention (important design choice):** the system answers "I cannot answer from the available data" when (a) the question contains an unknown name (a term absent from the corpus vocabulary — e.g. *Zorbatron-9000*, *SAP HANA*), (b) retrieval scores are below thresholds, or (c) the entity is unknown to the graph. **Why:** a security assistant that invents answers is worse than one that refuses; the course lists hallucination as the main LLM risk.
* **Grounding:** `verify_grounding` checks that every cited sentence is verbatim in the cited incident. It is 1.0 **by construction** for the extractive generator; its value is catching bugs and it will matter if Claude generation is switched on.
* **Why extractive by default:** offline, deterministic, cannot hallucinate, and every claim has a citation. The Claude path (`ClaudeGenerator`) uses a prompt built as the course teaches (instruction + context + input + output indicator, "only use the evidence, cite, abstain") but was **not executed** (no API key).
* **Neo4j:** see §3.12.

### 3.11 QA evaluation (`annotations/qa_testset.json`, `rag/evaluation.py`)

* **Before/after honesty.** The "before fixes" rows are the unbiased ones (`reports/qa_eval_before_fixes.json`). I fixed those rules; after the fixes graph answer-correctness is 1.00 on both sets and abstention recall 1.00, but those numbers are **tuned on the failing questions** and I quote the before-fix numbers as the honest ones.
* **Where the graph helps:** by question type (`reports/qa_eval.json::by_kind`): software→vulnerability 0.125 / 0.25 / **1.0** (vector / hybrid / graph) and vulnerability→software 0.0 / 0.375 / **1.0**; on open topical questions (characteristics, targets, incident lists) the three are close. Paired difference graph − hybrid in answer correctness on the main set: **+0.33 (95 % CI +0.19 to +0.47)**.
* **Why the graph wins on those questions:** the answer is a *relation* assembled from several records (or from the reference KB), which passage retrieval cannot do; this is exactly the course's table "Graph RAG vs RAG: multi-entity reasoning, traceability via explicit paths".
* **Limits (say them):** small sets written by the person who built the system; keyword matching is lenient for some "target" questions; the router's regexes are close to the main-set phrasings (that is why the paraphrase set exists); only one language pair tested.

## 6. Limitations and honest status (what is **not** solid)

1. **Data:** LLM-generated Q&A on concepts; some answers are factually wrong (flagged for CVEs only); 201 unfinished-reasoning rows dropped; no real incident reports; no IPs/hashes of interest (31 records with IPs).
2. **Labels:** weak labels are noisy (67 % agree with gold); the gold set has 183 records and one (AI) annotator — **review pending**; `phishing` has 13 records in total.
3. **NER:** recall 0.59 on a fresh sample (closed vocabulary); precision 0.97 on 137 audited mentions; no relation-label precision measured.
4. **KG:** relations are co-occurrence candidates with a typed label, not extracted verbs; reference KB has 21 CVEs only.
5. **Graph ML:** no gain over text features on this dataset (homophily 0.52, redundancy); link-prediction graph is tiny (≈ 325 edges), so standard deviations are large.
6. **Transformers:** only classification experiments; DistilBERT trained 3 epochs on CPU; generation experiments (Claude) not run.
7. **Neo4j:** code written, **not run on a live server**.
8. **QA evaluation:** small, self-written sets; results before fixes are the unbiased ones; grounding = 1.0 by construction.
9. **UI:** functionally tested (AppTest + live server probe) and inspected through headless-browser screenshots; not reviewed by a human user.
10. **Future work:** annotate more gold labels with 2 humans; supervised NER; relation extraction with a dependency parser or a fine-tuned model; larger KB (NVD/CISA KEV); run Neo4j and Claude generation; PEFT on a GPU.

## 7. Question bank (answers ready)

### Theory (course)
1. **TF-IDF?** weight = tf(w,d)·log(N/df(w)): frequent in the document, rare in the corpus. We use scikit-learn's sub-linear tf and smoothed idf.
2. **Cosine similarity?** cos(a,b) = a·b / (‖a‖‖b‖); on L2-normalised vectors it is a dot product → fast kNN and retrieval.
3. **Why LSA?** SVD of the TF-IDF matrix gives dense 128-d vectors that capture co-occurring terms; offline fallback for contextual embeddings.
4. **Self-attention?** Attention(Q,K,V) = softmax(QKᵀ/√d_k)·V: each token (node) takes a weighted average of values, weights from query–key similarity; multi-head = several such maps in parallel.
5. **Why RNN/LSTM were replaced?** sequential computation, vanishing gradients, limited memory; attention parallelises and links distant tokens (cost O(n²)).
6. **Encoder / decoder / enc-dec?** BERT-like understanding; GPT-like generation (causal mask); T5/BART seq2seq. We fine-tuned an encoder (DistilBERT).
7. **GCN formula?** H' = σ( D^-½ (A+I) D^-½ H W ): average of neighbours (and self) with degree normalisation, then a linear map.
8. **GAT?** weights α_ij = softmax_j(LeakyReLU(aᵀ[Wh_i ‖ Wh_j])) over neighbours: learned, node-pair-specific.
9. **GTN vs GNN?** GNN: fixed aggregation (mean/sum); GTN: Q/K/V attention over neighbours, edge-type bias for heterogeneous graphs, optional positional encoding, residual + LayerNorm + FFN.
10. **Why positional encoding for graphs?** attention alone ignores where a node sits; we use Laplacian eigenvectors (eigsh) with random sign flips.
11. **RAG vs fine-tuning?** fine-tuning changes weights; RAG injects external, updatable, citable knowledge at inference. Complementary (course slide 18).
12. **Graph-RAG vs RAG?** RAG retrieves similar passages; Graph-RAG also traverses entity relations → multi-entity answers with explicit paths/provenance (course table). Cost: building the graph.
13. **Precision@k / Recall@k?** P@k = relevant in top-k / k; R@k = relevant in top-k / all relevant. We cap recall at min(|rel|,k) when |rel| ≫ k. MRR = mean of 1/rank of the first relevant.
14. **Faithfulness?** the answer is supported by the retrieved evidence; we check it mechanically (verbatim citations).
15. **Chunking why?** context limits and finer retrieval; ~700 chars sentence-aligned.
16. **Louvain / modularity?** greedy optimisation of modularity Q = Σ [A_ij − k_i k_j/2m] δ(c_i,c_j)/2m.
17. **Lift?** P(a,b)/(P(a)P(b)): >1 means the pair co-occurs more than chance.
18. **What is leakage and how did you avoid it?** information from test data reaching training: one stored split, vectorisers fitted on train only, hyper-parameters on val, gold rows from test only, transductive GNN never uses val/test labels.
19. **Why macro-F1?** averages per-class F1 → rare classes count as much as frequent ones.
20. **LLM limits?** hallucination, bias, context window, cost, no causal understanding (course Chap. 3) — each seen here: LLM-written corpus errors, leaked CoT, 160-token truncation.

### About this project
21. *Is it a real incident dataset?* No — LLM-generated concept Q&A; stated everywhere.
22. *Why are your classification scores "only" ~0.65?* weak labels are inconsistent with gold (67 %); `other` has F1 0.24 on gold; the metric is honest.
23. *Why didn't the Transformer win?* §3.5.
24. *Why didn't the GNN win?* §3.9: homophily 0.52, redundancy, noisy labels.
25. *How do you avoid hallucinations?* extractive generation, abstention gate, per-claim citations, KB verification flags, grounding check.
26. *What if the question is not in the data?* it refuses: after the fixes all 8 + 3 unanswerable test questions are refused; before the fixes 7/8 (main) and 2/3 (paraphrase) were — see §3.11.
27. *How did you evaluate QA?* §3.11, with before/after.
28. *What is the reference KB and why is it legitimate?* small, curated, labelled `reference_kb`, used for gap filling and fact-checking; not mixed silently with corpus facts.
29. *Does it run with Neo4j?* §3.12 — written, not run live.
30. *How is it reproducible?* `config.toml` (seed 42), pinned `requirements.txt`, deterministic pipeline, 57 tests.
31. *Who annotated?* an AI assistant, blind; review procedure in `docs/ANNOTATION_GUIDELINES.md`.
32. *What would you do with more time?* §6.10.
